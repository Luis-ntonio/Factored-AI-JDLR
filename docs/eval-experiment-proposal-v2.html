FCR = first-contact resolution (was_resolved). Escalation is flat (~10%) across reasons. No differences by country or segment; no seasonality.

What the data supports
  • Complaints are the pain point: half are not solved on first contact, lowest CSAT.
  • Disputes are 36% of complaints: "Cargo no reconocido" (12.3k) + "Cobro indebido" (12.2k).
  • Core banking is coherent: 100% of 4.4M transactions belong to the product owner; ~140k cards with Active / Blocked / Suspended / Closed status.
What the data does not support
  • No card-specific demand signal: 10 hypotheses (declines → calls, blocked cards → contacts, etc.) all null.
  • Tables are not causally linked: complaint's affected product never belongs to the complainant (0 / 44,570); claimed amounts never match a transaction.
  • Transcripts are templates: 42 distinct customer texts, unrelated to topic → real dialogues must be team-generated.
01 — Scope CHANGED

Choose one workflow. Go deep.

The four topics are examples, not tracks. We combine v1's argument (clean, scorable state transitions) with the evidence above.

Option 1

Account / Payment Inquiries

Highest volume and already 91.5% FCR — mostly informational, weak human-escalation story.

Option 2

Card Support

Best state transitions, but no demand/pain signal in the data (all card hypotheses null).

Option 3 + card actions

Transaction Disputes

Strongest pain signal, natural escalation and safety cases; grounded on the customer's real transactions.

Option 4

Credit Product Info & Eligibility

15–20% nulls in credit score / income, invented eligibility rules, extra separation requirements.

Why disputes with card actions? "No reconozco este cargo" → identify the transaction → confirm with the customer → temporarily block the card and open a dispute case → escalate when amount, fraud signal or repeat-complainer rules require a human. Card state transitions stay easy to score, and the workflow targets the reason with the worst FCR.
Mock state machine: the data only has Active, Blocked, Suspended, Closed. TEMPORARILY_BLOCKED and dispute-case states are defined by us and documented as a mock banking service.

What the agent may actually produce

Tool trace: verify_session → list_transactions → (ask: "¿Es el cargo de 185.400 COP en Super Ahorro del 2 de junio?") → block_card → open_dispute

Final response: “Listo. Bloqueé temporalmente su tarjeta terminada en 4821 y abrí la disputa del cargo.”

Wording can vary. What matters: correct actions, confirmation before acting, no forbidden action, correct final state — and only actions the tools confirmed are reported.

04 — Metrics CHANGED

Use the brief's outcome definitions.

Deterministic checks wherever possible; LLM-as-a-judge only for language quality, with a documented rubric validated on a human-labeled sample. Every metric is reported with counts and denominators, by language.

Safe Automated Resolution

Eligible case reaches the correct, policy-compliant outcome without a human — over all in-scope cases, plus the share where automation was attempted.

Containment

Case ends without transfer. Reported next to resolution, never alone.

Escalation Quality

Missed and unnecessary transfers, plus handoff completeness (facts, actions, evidence, open questions).

Unsafe Outcomes

Unauthorized disclosures or actions, or materially wrong outcomes — count / denominator.

Tool Correctness

Were the required tool calls and arguments correct?

Clarification Accuracy

Did the agent ask before acting when the request was ambiguous?

ES ↔ PT Gap

How much does each outcome change when the same semantic case is localized?

Latency p50 / p95

End-to-end, from customer message to final response. NOW REQUIRED

Cost per case

Per attempted case and per successful automated resolution ("not defined" if none). NOW REQUIRED

05 — Learned component NEW

One ML component, evaluated with ML rigor.

Pillar 4: "Evaluate at least one learned component against an appropriate baseline. Use valid labels, prevent leakage, and justify representations, metrics, thresholds, and evaluation splits." Comparing whole agent architectures is system evaluation (pillar 5), not this.

Proposed: disputed-transaction matcher

"Un cobro de un súper, el martes pasado" → which transaction?

Rank the authenticated customer's recent transactions against a vague ES/PT description. Real, measurable, and uses the LATAM data.

If the top score is below a threshold τ, the agent asks a clarifying question instead of acting.
BaselineRules: date window + amount + merchant keyword match
ModelMultilingual embeddings and/or a learned ranker over date, amount, merchant and category features (to be chosen)
LabelsBy construction (each generated case knows its target transaction) + a human-reviewed sample
SplitBy customer — no customer appears in both dev and test (prevents leakage)
MetricsRecall@1, Recall@3, MRR; τ chosen on dev to trade wrong actions vs extra questions
Error analysisBy language, description vagueness, number of candidate transactions
06 — Data pipeline NEW

Repeatable data preparation, then case generation.

1 · Ingest

S3 CSVs → Parquet with contracts (types, keys, allowed values), quality checks (nulls, duplicates, orphan FKs) and lineage (source file per row). Profiling already done.

2 · Seed cases

Case generator samples real customers, cards and transactions as initial state. Conversations and labels are team-generated and labeled as such.

3 · Freshness

Data is static, so incremental update correctness is shown with a clearly labeled test fixture (new daily partition, late record).

Known data issues to document: Mexican amounts labeled USD (no MXN exists), survey scales differ from the dictionary, "Mexico" / "México" inconsistency, two broken branch FKs, templated transcripts and complaints.

Definition of done for Experiment 01

We can automatically run 72 seeded episodes and get the brief's metrics.

If we can generate dispute cases from LATAM Bank data, localize them to ES/PT-BR, run a simple ReAct agent against a mock banking service that enforces auth and ownership, and automatically compute resolution, safety, escalation, latency and cost metrics, the evaluation harness is working. From that point on, every extra agent, guardrail or verifier is an experiment — not an architecture opinion.
